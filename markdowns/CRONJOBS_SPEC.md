# Cronjobs Specification

## Goal

Add cronjob automation to pi.lot with the smallest possible implementation surface.

The system must allow the authorized Telegram user to create, list, edit, delete, and execute scheduled prompts. When a cronjob is triggered, pi.lot should start a fresh pi session, submit the cronjob prompt as if it had been sent by the Telegram user, and deliver progress/final output through the normal Telegram output flow.

## Design principle

- Keep pi.lot orchestration simple.
- Prefer a standalone pi skill for cronjob management if feasible.
- Use the Linux cron service available inside the container for scheduling.
- Reuse the existing Telegram prompt execution path instead of adding a parallel execution system.
- Reuse existing pi session handling: every cron execution creates a new pi session.
- Avoid broad application changes; introduce only a small bridge between system cron and the existing pi.lot prompt runner.

## Functional requirements

### Cronjob model

A cronjob consists of:

- `id`: stable unique identifier generated by pi.lot.
- `name`: optional human-readable name.
- `schedule`: cron expression or supported recurrence shortcut.
- `timezone`: optional; defaults to the Docker host/container timezone.
- `prompt`: required text sent to pi when the cronjob runs.
- `enabled`: boolean, default `true`.
- `created_at`: timestamp.
- `updated_at`: timestamp.
- `last_run_at`: optional timestamp.
- `last_status`: optional status/result summary.

### Supported operations

- Create cronjob.
- List cronjobs.
- Show cronjob details.
- Edit cronjob schedule/name/prompt/enabled state.
- Delete cronjob.
- Execute cronjob immediately, independent of schedule.
- Enable/disable cronjob.

### Recurrence / schedule input

Persisted format:

- Raw five-field Linux cron expression: `minute hour day-of-month month day-of-week`.

User-facing input may be natural language. The LLM/skill should convert natural-language recurrence requests into explicit cron syntax before creating or editing a cronjob.

Supported shortcuts:

- `@hourly`
- `@daily`
- `@weekly`
- `@monthly`

Unsupported:

- `@reboot` is not supported because it may run before Telegram/pi are ready.

Natural-language scheduling is expected for the user interface, but persisted cronjobs must store the resolved cron expression.

## User interface

Preferred: standalone pi skill exposing cronjob commands/tools to pi.

The Telegram user can ask naturally, for example:

- `Create a cronjob every weekday at 8:00 that asks pi to summarize my todos.`
- `List my cronjobs.`
- `Run cronjob 3 now.`
- `Disable the weekly report cronjob.`
- `Change cronjob 2 to run every day at 18:00.`

Optional direct slash commands may be added only if needed:

- `/cron_create <schedule> | <prompt>`
- `/cron_list`
- `/cron_show <id>`
- `/cron_edit <id> ...`
- `/cron_delete <id>`
- `/cron_run <id>`
- `/cron_enable <id>`
- `/cron_disable <id>`

If implemented as a skill, slash commands are not required for version 1 of cronjobs.

## Runtime behavior

### Scheduled trigger flow

1. Linux cron triggers a lightweight command inside the container.
2. The command calls a small pi.lot cron execution entrypoint with the cronjob `id`.
3. pi.lot loads the cronjob definition.
4. pi.lot creates a new pi session.
5. The cron-created session is registered in normal session management and appears in `/sessions`.
6. The currently active Telegram session remains unchanged. Cronjob sessions are inserted into normal session history and can be selected later by the user, but they do not become active automatically.
7. pi.lot submits the cronjob prompt using the same internal path as a Telegram user prompt.
8. pi.lot sends thinking/progress/final output to the authorized Telegram chat using the existing Telegram output mechanism.
9. Cronjob output is always sent to Telegram.
10. pi.lot updates `last_run_at` and `last_status`.

### Manual execution flow

Manual execution should use the same execution path as scheduled execution, except it is triggered by user request instead of Linux cron.

## Storage

Cronjob definitions should be persisted in a simple local file, for example:

- `data/cronjobs.json`

The system cron table should be treated as generated state derived from `cronjobs.json`.

Cronjob persistence should ideally use a Docker-mounted data volume so cronjobs survive container replacement/rebuilds. Recommended approach:

- Store cronjob definitions under a configurable data directory, defaulting to `/data` inside the container.
- Mount a host directory or named Docker volume to `/data`.
- Store cronjobs at `/data/cronjobs.json`.
- Optionally store cron execution logs/history under `/data/cron/` later.
- On application startup, load `/data/cronjobs.json` and regenerate Linux crontab entries from it.

This keeps the implementation simple: only the JSON source of truth must be persistent; Linux crontab can always be regenerated.

Whenever a cronjob is created/edited/deleted/enabled/disabled, pi.lot regenerates the relevant cron entries.

Recommended cron entry shape:

```cron
# pi.lot cronjob: <id>
<schedule> /usr/local/bin/python -m pilot.cron_runner <id> >> /var/log/pilot-cron.log 2>&1
```

Exact module/path can be adjusted to the final project structure.

## Skill shape

Best-case standalone skill responsibilities:

- Parse user intent for cronjob management.
- Convert natural-language schedules into explicit cron expressions.
- Validate or normalize schedules.
- Call small pi.lot cron management tools/functions.
- Return concise confirmations and lists.

The skill should not independently run Telegram or pi sessions. It should call into pi.lot-managed cron APIs/files so there is one source of truth.

Potential skill tools:

- `cron_create(schedule, prompt, name=None, timezone=None)`
- `cron_list()`
- `cron_get(id)`
- `cron_update(id, schedule=None, prompt=None, name=None, enabled=None, timezone=None)`
- `cron_delete(id)`
- `cron_run(id)`

## Minimal implementation approach

1. Add persistent cronjob store.
2. Add cron manager functions for CRUD and crontab regeneration.
3. Add cron runner entrypoint that accepts a cronjob id and invokes existing prompt execution flow with a new session.
4. Add standalone pi skill/tool definitions that call the cron manager.
5. Ensure container has cron installed and running.
6. Add logs for cron execution failures.

## Security and authorization

- Only the already authorized Telegram user may manage cronjobs.
- Scheduled executions always send output to the authorized Telegram chat.
- Cronjob prompts are trusted at the same level as normal prompts from the authorized Telegram user.
- Do not allow arbitrary shell commands in cron entries; cron entries should only call the fixed pi.lot runner with a validated cronjob id.

## Error handling

- Invalid cron expressions should be rejected with a clear error.
- Missing/deleted cronjob id should fail visibly in logs.
- If scheduled execution fails, send a Telegram error message if possible and update `last_status`.
- If cron service is unavailable, cron management should return a visible error.

## Clarified decisions

- Cronjobs should persist across container rebuild/replacement if a Docker volume or host directory is mounted to `/data`.
- Schedules use the Docker host/container timezone.
- Overlapping executions are allowed. The lowest-effort implementation may simply let them run in parallel, even if this temporarily sends multiple Telegram progress messages.
- Cron-created sessions should appear in `/sessions`.
- Cronjob output is always sent to Telegram.
- Natural-language scheduling should be supported by having the LLM/skill convert user intent into explicit cron syntax before persistence.
- Scheduled cronjob prompts should use the recommended/lower-effort execution path. Parallel execution in separate pi sessions is acceptable.
- The active Telegram session must remain unchanged when a cronjob creates a session. Cronjob sessions are visible in `/sessions` but only become active if the user switches to them manually.
- Editing supports partial field updates only.
- No explicit limits are required for number of cronjobs, prompt length, or execution duration.
- Cronjob history only needs `last_status` for now.
- Cronjobs should be included in backup/export functionality later.
- `@reboot` cronjobs are not supported.

## Remaining open points

None for the current cronjobs specification.
